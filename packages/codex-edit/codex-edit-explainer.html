先解释指标

“编辑协议失败：1 → 0”到底是什么？

这是本次 benchmark 自定义的分类名，不是 HTTP、Responses API 或 custom tool 协议错误。

A · 当前 edit

1 次工具调用失败，但任务后来完成

公平 A 组中唯一被归类为协议失败的是 11-bom。模型先读取了带 UTF-8 BOM 的文件，然后调用 Pi edit，把 BOM 放进了 oldText。Pi 的精确匹配没有找到这段文本，于是返回：

Could not find the exact text in src/bom.js
old text 必须逐字匹配，包括空白和换行。

模型随后使用 bash 做了字节级修改，最终文件正确，所以“最终正确率”仍算成功；但“首次编辑成功率”和“编辑协议失败”仍记录了这次失败。

C · apply_patch

工具协议直接匹配模型的 Codex 先验

GPT-5.6 在 C 组中以 apply_patch 的名字调用 custom tool，输入是原始 patch 文本，而不是嵌套的 path + edits[] JSON。19/20 个公平用例出现了可识别的 custom call，且没有编辑工具执行失败。

因此“1 → 0”表示：首次编辑环节少了一次失败调用。它不是说所有文件修改错误都消失了，也不是说 API 从不失败。

最终正确率仍然是 90%，因为剩余问题属于内容语义或文本格式细节，例如换行转义和引号选择。

Architecture

工具的完整调用链

关键设计是“模型看到哪种工具”与“工具如何安全落盘”分开。

01 · Model state当前模型配置

ctx.model.provider、api、id、compat 能力标记。

→
02 · RoutingsyncEditorTools()

GPT/Codex grammar 模型启用 apply_patch；其他模型启用 edit。

→
03 · ProviderResponses serializer

Grammar 支持时序列化为 type=custom + Lark definition。

→
04 · Executionparse → validate → apply

完整解析、路径检查、预校验，最后才写文件。

信任边界：grammar 只约束模型输出形状，不等于 sandbox。路径、软链接、目录、覆盖和权限必须由执行端再次检查。
Execution

一次 apply_patch 如何落盘

先把 patch 变成可信的 change plan，再进入写入阶段。

01 / RECEIVE
接收原始 patch

模型发出 Begin Patch 到 End Patch 的自由格式文本。

02 / PARSE
解析成 AST

Add、Delete、Update、Move 和多个 update chunk。

03 / RESOLVE
解析路径

相对路径以 ctx.cwd 为根，允许 workspace 内绝对路径。

04 / PREFLIGHT
全部预校验

读取快照，匹配上下文，计算每个文件的新内容。

05 / MUTATE
串行写入

通过 mutation queue 写入；移动先写目标再删源。

06 / REPORT
返回 diff

返回逐文件 diff、unified patch、已提交路径和失败前缀。

Design principles

这个工具的三个核心原则

模型协议对齐

GPT/Codex 模型不再被要求适应 Pi 自定义的 oldText/newText JSON；它看到原生的 apply_patch 名称和 patch grammar。

执行端独立防护

grammar 不是安全策略。执行端仍要做 workspace 边界、符号链接、目录、覆盖冲突、权限和取消检查。

按能力选择，不靠 AGENTS 对抗

不在 AGENTS 中要求模型“不要使用 apply_patch”。扩展只让模型看到适合自己的一个编辑工具，避免两套协议同时暴露。
